## 流程

1. `blender/render_prod.py --target <兵種>`：算 3 倍原始素材。
   - 每個方向開一個 Blender。
   - 圖層：本體、玩家色遮罩、影子（半解析度）、環境光遮蔽，法師另有特效層（不含防護罩）和防護罩層。
   - 輸出到 `build/prod/<兵種>/raw/`。
2. `common/postprocess.py --target <兵種> --scale 3|2 [--team-gain 1.6] [--astc 4x4]`：修邊、打包成圖集、算記憶體。
   - 倍率和壓縮是參數。client 在 iPhone 實測、D-017 定案後，只要重跑這一步。
   - 格式照 client 的規格第 2 版（`client/docs/sprite-atlas.md`，2026-10-01）：
     - 各層各自修邊排版：顏色、玩家色（RGBA）、影子（黑色加透明、半解析度、8 個方向）、法師特效、法師防護罩。
     - 說明檔 `war-game atlas 2`：
       - 每個動作有 fps；攻擊有 `hit`（出手那一格），工作動作也有 `hit`（工具打到那一格，`spec.WORK_HIT`）。
       - 倒下（法師是 `fall`）有 `impact`：身體落地那一格，遊戲在那裡畫共用的落地揚塵；大的單位另有 `impact_scale`（`spec.IMPACT`）。
       - 攻城器械的走路有 `stride_m`：一個循環前進幾公尺（`spec.STRIDE_M`），client 用它算播放速度，輪子不會滑。
       - 另有 team 表；法師另有 `shield` 一塊（`anims` 與 `frames`）和 `pages.shield`。
     - 沒有內容的影格不列：沒有玩家色的格不進 team 表，沒有特效的格不進 fx 表。
   - 記憶體：未壓縮一律每點 4 位元組（灰階 PNG 上 GPU 也是 RGBA8），ASTC 4×4 每點 1 位元組。
   - 頁寬 2048，頁高補到 4 的倍數。頁內先放高的影格，影格約佔頁面的 86%。
   - 玩家色層照 client 的相乘畫法，實際大小就看得出比 R5 核准的樣子暗（黃色變橄欖色、白色變灰）。
     - 後處理把玩家色層乘上 team_gain 1.6（1 ÷ 0.62，R5 換色的基準亮度），超過白色就截斷。這樣和 R5 幾乎一樣。
     - 預設 1.6：ceo 2026-10-01 看過藍、紅、黃、近白四色對照後定案。不用柔和壓縮，也不加亮部那一層。
     - 對照圖由 `common/team_compare.py` 產生。
     - 玩家色不選近白色，因為中立的東西（野城民兵、大城箭樓）在原型裡是灰白色（client 的 NEUTRAL_TINT 0xd8d2c0）。
       4 種玩家色在 R6 正式介面一起定案。
3. `common/checks.py --target <兵種>`：自動檢查，並出每個兵種的縮圖總表（列是動作，欄是 8 個方向，鏡像方向是翻轉後的樣子）。
   - 硬性檢查，不過就算失敗：缺圖、本體碰到畫框、空白影格、錨點或影格大小不一致。
   - 法師另查：防護罩每一格都在、不是空的、沒碰到畫框；待機、走路、受擊的特效層要是空的（防護罩留在特效層會畫兩次）。
   - 警告：影子或特效碰到畫框、玩家色太少。
4. `common/effects.py --scale 3|2`：共用的世界效果圖集 `effects.json` 加 `effects_0.png`（現在只有落地揚塵 `dust`），不用 Blender。

算圖在 GitHub Actions 上跑（`design-render`，round 選 production，每個兵種一個 job）。
- 每個 job 上傳兩份：
  - 報告：`production-<兵種>-report`。
  - 原始素材加圖集：`production-<兵種>`。
- target `effects` 產生世界效果圖集，上傳成 `production-effects-atlas`。
- 都保留 90 天，原始素材留著是為了之後重跑後處理。

```bash
gh workflow run design-render --ref <分支> -f round=production \
  -f targets='["farmer_e","spear_e","xbow_e","hcav_e","siege_e","mage_e","farmer_w","pike_w","bow_w","knight_w","siege_w","mage_w","effects"]'
```

- 同一條分支再送一次會取消還在跑的那次（`concurrency`）。要同時跑兩組，就把同一個 commit 推到另一條分支再送。

本機只在 available ≥ 2 GB 時跑 `--preview`（每個動作第一格、低取樣），一樣用記憶體上限區。

## 畫框自動量

- 算圖前先跑一次只擺姿勢、不算圖的量測（`render_units.py` 的 fit 模式）：
  - 每個動作的每一格、8 個方向都擺一次。
  - 量出兵種在畫面上往四個方向伸得最遠的距離，四邊各加 0.12 公尺，當成這個兵種的畫框。
  - 法師的魔法陣和防護罩算進畫框。飛出去的晶砲不畫進人物圖，照 client 的規格由遊戲畫成彈道。
- 起因：第一次全部算圖（run 36694860969），12 個兵種有 10 個被切到。
  - 朝向 2（背對鏡頭）時，往前伸的武器和背旗在畫面上會往上跑。
  - 倒下時身體往側面倒。
  - 霹靂車的拋竿往後甩。
- 圖集會修邊，畫框大只多花算圖時間，不佔記憶體。

## 防護罩單獨一層（圖集格式 2）

- 依據：client 規格第 2 版第 4 節（ceo 2026-10-01：防護罩拆成單獨的圖，遊戲在快照的 `shield` > 0 時疊上去）。
- 特效層不再算防護罩，只剩魔法陣、晶彈閃光、破盾碎片。防護罩另外算 `on`、`hit`、`break` 三個動作，只算朝向 7、不鏡像
  （防護罩是繞垂直軸對稱的橢球，8 個方向的外形一樣）。
- **做法：身體大小的替身遮住後半面**（ceo 2026-10-01 採用 D）。
  - 核准的樣子（R5、P1-02）是身體擋住防護罩的後半面。拆開後的防護罩要疊在任何一格身體上，不能照某一格的身體挖空。
  - 所以算防護罩時放一個看不見、但會擋住後面東西的替身（Blender 的 holdout）。它是一個繞垂直軸轉出來的人形輪廓：
    - 半徑（公尺）由腳到頭：0.27（腳下）、0.27（0.15 高）、0.23（0.6）、0.21（腰 1.05）、0.23（胸 1.3）、0.20（肩 1.42）、
      0.08（脖子 1.5）、0.11（1.58）、0.12（頭 1.72）、0.08（1.84）、0（頭頂 1.88）；
    - 前後方向壓扁成 0.8 倍；跟著單位的根節點，不跟著動作動。
    - 程式：`blender/render_units.py` 的 `BODY_PROXY` 與 `_body_proxy()`；job 旗標 `shield_proxy`（預設開）。
  - 替身只遮後半面：前半面在替身前面，照樣畫出來。
- **驗證**（`common/shield_compare.py`）：照遊戲的順序（顏色、玩家色、防護罩、特效，一般混合）合成，和核准的 A 並排。
  比待機、受擊最亮的那一格、破盾第 1 格，兩種法師。
  - B：整顆防護罩都畫（規格原本的寫法）。身體上多了一層霧，明顯偏淡。
  - C：只算朝鏡頭的半面。身體不霧了，但身體周圍的防護罩變薄。
  - D：替身遮後半面。實際大小下和 A 分不出來。差別只在受擊時舉起來的手臂和袖口（伸出替身之外），只有受擊那幾格。
