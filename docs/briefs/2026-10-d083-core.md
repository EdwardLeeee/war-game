## 範圍（`sim/`）

1. **人口規則**：
   - 做成規則開關，預設關。關著時和 main 逐局相同；war-game-ai 重調完，由最後一個 PR 打開。
   - 開關打開時：
     - 天花板 = 200 ＋ 每座治理中的小鎮 20 ＋ 大城 40。隨機地圖全拿最多 360，固定地圖最多 300。
     - 治理城鎮給的人口：小鎮 +20、大城 +40（原本 +5／+10）。
     - 城鎮被搶、叛離、變廢墟時，天花板跟著降。已經有的單位不會消失，只是不能再訓練。
     - 混戰的上限（GDD 寫每方 100）原型沒有，這次不動。
   - 畫面要知道目前的天花板（資源列的人口、每兵種上限都要用）。怎麼放進 PlayerView 由你提，寫進 PROTOCOL.md。
   - 數值寫在 `rules()` 裡，電腦一律從 `rules()` 讀（failure.wargame.ai_sized_from_default_constant_not_live_rules）。
2. **perf 場景**：
   - 照現在的 perf 場景，多做兩種：兩邊各 200、各 360 人口，村民和兵的比例照現在。
   - 「量測」選單怎麼選這兩種，和 war-game-client 講好。
   - 先在 CI 上量：
     - 每 tick 模擬的中位數、最慢 5%、最大。
     - 拿來對照的是現在的 120 場景。
   - 回報 ceo 以後，ceo 再請使用者用 iPhone 量。標準照舊：fps 中位數 ≥ 55、最慢 5% ≥ 30、每 tick 中位數 ≤ 5 ms。
3. **快轉後接著打**（給「繼續上一局」用）：
   - 模擬收到一份紀錄（現在 `exportLog` 匯出的 jsonl）和要快轉到的 tick：
     - 電腦照常在模擬裡算，玩家的指令用紀錄裡的。
     - 快轉到那個 tick 以後，接著用正常速度跑，指令紀錄接在後面。
   - 檢查：
     - 快轉時電腦下的指令要和紀錄裡的一樣，雜湊要對上紀錄裡的雜湊。對不上就回報錯誤，不要接著打。
     - 紀錄的 commit 或協定版本和現在的不同時，不能繼續，回報原因。網站更新以後，舊的對局就接不下去了。
   - 要回報快轉的進度，畫面才能顯示。
   - 介面寫進 PROTOCOL.md，和 war-game-client 講好再定。
   - 量一局 80 分鐘（約 96,000 tick）的紀錄，在 CI 上快轉要多久；iPhone 大約多久，由你估。

## 驗收

- 開關關著：電腦對電腦、腳本玩家各組都和 main 逐局相同。
- 開關打開：
  - 單元測試：天花板跟著治理的城鎮升降；超過天花板就不能訓練；城鎮丟了，已經有的兵不會消失。
  - 拿掉修正會失敗的測試，至少一個。
- 快轉：
  - 測試：同一局在第 N tick 中斷再接著打，和一路打下來的雜湊相同。N 要涵蓋電腦正在出兵、正在撤退這些時候。
  - 紀錄被改動、commit 不同時，回報錯誤。
- perf：CI 上 120、200、360 三種的每 tick 時間。
- 回報 CI 時，依 head SHA 列出全部 run。

## 流程

- 先把計畫回給 ceo（簡短），核准後開始。
- 從 origin/main 開新分支。開關預設關，所以人口規則和 perf 場景的 PR 不改變試玩版本，CI 綠了 ceo 就合併。這樣使用者就能在線上量 iPhone。
- 快轉的 PR 會讓 client 有新功能，第一行寫「會改變試玩版本」（如果有）；合併時機由 ceo 決定。
